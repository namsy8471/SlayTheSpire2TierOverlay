# 삽입 안정 셔플 (키드 모드 전용) 작업 계획

작성 2026-11-10. 계획: Fable 5.2, 구현: Opus 5.5. 상태: **사용자 승인 (2026-11-10), 구현 중** (엔진 패치와 측정 결과는 다음 PR).
배경과 수치는 `LEARNED_CARD_POLICY_PLAN.md` 5.6.2, 5.7.

## 1. 왜 하나

카드 한 장의 시뮬 가치는 "덱" 과 "덱 + 카드" 를 같은 시드로 싸우게 해서 잰다. 지금 2시드 측정의 신뢰도는 비용 0.41, 화면 안 0.55 다. 잡음의 가장 큰 원인은 셔플이다.

```
덱 A        = [a b c d e f g h i j]      시드 s 로 섞음 → [d a j c ...]
덱 A + X    = [a b c d e f g h i j X]    같은 시드 s   → [h X b f ...]   ← 전혀 다른 순서
```

sts2-sim 의 셔플은 피셔-예이츠(뒤에서부터 무작위 자리와 교환)다. 카드가 한 장 늘면 첫 교환부터 달라져서 나머지 카드의 순서도 전부 바뀐다. 그래서 "X 를 넣어서 좋아졌나" 와 "그냥 손패 운이 달랐나" 가 섞인다. 키드 난수 모드는 셔플마다 난수를 따로 뽑아 주지만(`CombatState.NextShuffleRng`), 셔플 알고리즘이 같아서 이 문제는 그대로다 (시험 결과: 신뢰도 0.36 → 0.31, 개선 없음).

## 2. 무엇을 바꾸나

키드 모드에서만, 셔플을 "카드마다 고정 난수 키를 뽑아 그 키로 정렬" 로 바꾼다.

```
키(card) = hash(런 시드, 전투 키, 셔플 순번, 카드 꼬리표)
섞은 순서 = 키 오름차순
```

- 카드마다 독립인 균등 난수 키로 정렬하면 결과는 균등 무작위 순열이다. 분포는 피셔-예이츠와 같다.
- X 를 넣어도 a…j 의 키는 그대로이므로 **a…j 끼리의 순서는 그대로**이고 X 만 어딘가에 끼어든다.

```
덱 A      → [d a j c g b i e h f]
덱 A + X  → [d a j X c g b i e h f]
```

**카드 꼬리표** (전투 안에서 카드 한 장을 가리키는 고정 이름):
- 덱에서 온 카드: `deck/{카드 ID}/{강화 단계}/{같은 (ID, 강화) 중 덱 순서로 몇 번째}`. `Player.PopulateCombatState` 에서 전투 복사본을 만들 때 붙인다. 새 카드는 덱 끝에 추가되므로 기존 카드의 "몇 번째" 는 두 덱에서 같다.
- 전투 중 생긴 카드(단검, 상태이상, 복제): `gen/{카드 ID}/{이 전투에서 그 ID 로 몇 번째 생성}`.
- 꼬리표는 만들 때 한 번 정하고 **전투 중 강화돼도 바꾸지 않는다** (바뀌면 다음 셔플에서 자리가 튄다). 카드 복제(`MutableClone`, `CombatState.Clone`)는 꼬리표를 그대로 복사한다.

## 3. 고칠 곳 (sts2-sim, `src/Sts2Sim.Core`)

| 파일 | 지금 | 바꿀 것 |
|---|---|---|
| `Models/CardModel.cs` | – | `internal string? ShuffleTag` 추가, 복제 경로에서 복사 |
| `Entities/Players/Player.cs` `PopulateCombatState` | 전투 복사본 생성 후 `RandomizeOrderInternal(shuffleRng)` | 키드 모드면 복사본마다 `deck/…` 꼬리표 부여 |
| `Combat/CombatState.cs` | `NextShuffleRng()` 가 순번을 올리고 Rng 반환 | 키드 전용 `NextShuffleKey()` (같은 순번 증가, 문자열 키 반환) 추가. `CloneNextShuffleRngForProjection` 을 쓰는 곳이 다음 셔플을 미리 볼 때 같은 정렬을 쓰는지 확인 |
| `Entities/Cards/CardPile.cs` `RandomizeOrderInternal` | `rng.Shuffle(list)` | 키드 모드 분기: 키 정렬 |
| `Commands/CardPileCmd.cs` `Shuffle` | `combined.StableShuffle(shuffleRng)` | 키드 모드 분기: 키 정렬. 그 뒤의 `ModifyShuffleOrder`(인챈트) 는 그대로 |
| 카드 생성 지점 (`CardPileCmd` 의 생성 명령) | – | 키드 모드면 `gen/…` 꼬리표 부여 (전투별 ID 카운터는 `CombatState` 에, 복제 시 복사) |
| `Random/KeyedRngSeed.cs` | `Derive(seed, stream, key)` | 그대로 재사용: `Derive(seed, "shuffle", $"{전투 키}/shuffle_ordinal={n}/card={꼬리표}")`. 동률은 꼬리표 문자열 순 |

규칙:
1. **순차(일반) 모드는 한 줄도 동작이 바뀌면 안 된다.** 키드 분기는 `RunState.Rng.UsesSemanticKeys` 로만 들어간다. 불리언 인자로 두 알고리즘을 합치지 않는다 (sts2-sim 의 기존 방침).
2. 선천성(Innate), 맨 아래 시작 인챈트처럼 셔플 **뒤에** 적용되는 규칙은 건드리지 않는다.
3. 맵 생성 등 다른 `StableShuffle` 호출은 건드리지 않는다. 전투 덱 셔플 두 곳만.
4. 속도 패치와 섞지 않는다. 산출물은 `sts2-sim-perf.patch` 위에 얹는 별도 파일 `sts2-sim-keyed-shuffle.patch`.

| 1 | 일반 모드 불변 | `req_v2.jsonl` 앞 200줄을 패치 전·후 빌드로 돌린 결과 파일의 해시가 같다. 전투 AI 스레드의 600전투 기준 파일과도 같다 |
| 2 | 삽입 안정성 | 테스트: 같은 시드, 덱 A 와 A + X. 전투 시작 뽑을 카드 더미에서 X 를 빼면 A 의 순서와 완전히 같다. 카드 20종 × 시드 50개 |
| 3 | 다시 섞기 | 테스트: 버린 카드 더미 구성이 같은 두 상태(한쪽에 X 추가)에서 다시 섞은 뒤에도 2번과 같은 성질 |
| 4 | 균등성 | 10장 덱, 시드 10,000개: 특정 카드가 각 자리에 올 빈도가 10% ± 1.5%p |
| 5 | 결정성 | 같은 요청을 두 번 돌리면 결과가 같다. `CombatState.Clone` 뒤 복제본의 다음 셔플 = 원본의 다음 셔플 |
| 6 | 꼬리표 유지 | 전투 중 강화(Armaments 류) 뒤에도 꼬리표가 같다. 전투 중 생성 카드가 꼬리표를 가진다 |

## 5. 효과 측정 (Fable 이 분석)

수정된 엔진, 같은 400 화면(`req_v2.jsonl`), 2시드, `SIMLAB_KEYED=1` + 이 패치. 약 10분 (4프로세스 × 6스레드, 진행률 파일).

비교 대상은 같은 엔진의 일반 모드 결과 `value_v2f.csv`:

| 지표 | 지금 (일반 모드) | 성공으로 볼 기준 |
|---|---|---|
| 비용 2시드 신뢰도 (전체 / 화면 안) | 0.38 / 0.58 | 화면 안 0.70 이상, 화면 단위 부트스트랩 90% 구간이 지금 값을 벗어남 |
| 턴 수 (전체 / 화면 안) | 0.58 / 0.73 | 떨어지지 않음 |
| 랭커가 시뮬 최고 카드를 고른 비율 | 51.0% [46.7, 55.6] | 떨어지지 않음 (잡음이 줄면 오르는 게 자연스러움) |

기준을 넘으면: 1,400 화면을 이 모드로 다시 뽑아 시뮬 가치 모델을 다시 학습하고, 전체 런 하네스(5.7)의 반사실 라벨에도 이 모드를 쓴다. 못 넘으면: 패치는 보관만 하고, 남은 잡음은 "AI 가 다른 수를 둬서 갈라지는 것" 으로 보고 시드 수를 늘리는 쪽으로 간다.

못 줄이는 것 (이 패치의 범위 밖): X 가 손에 들어온 뒤 AI 가 다른 카드를 내서 전투가 갈라지는 차이. 이것은 잡음이 아니라 재려는 효과다.

## 6. 주의

- 키드 모드는 게임의 실제 난수 순서와 다르다. **선택지끼리의 차이(라벨)** 를 잴 때만 쓰고, "실제 게임과 얼마나 같은가" 검증(전투 AI 스레드의 홀드아웃)은 계속 일반 모드로 한다.
- sts2-sim 은 오프라인 전용이다. 이 패치도 오버레이 배포물에 들어가지 않는다.
- SimLab 의 `SIMLAB_KEYED` 스위치(`CombatRunner` 2줄)는 PR #40 브랜치에 넣어 달라고 전투 AI 스레드에 요청한다.
