# 덱 시뮬레이션으로 본 카드 추천 점수 (v0.107.1)

> 오버레이 추천을 그대로 따라 런을 2,000번 돌려 보고, 상위 랭커의 실제 승리 덱 130개와 비교했습니다.
> 빌드는 거의 항상 완성되지만, **코어 카드가 없는 빌드를 지키지 못하고, 빌드 카드를 겹쳐 쌓지 못하고, 3막에서 스킵을 너무 많이 권하는** 문제가 있었고,
> 이 셋과 "빌드 축 과잉 생산" 규칙을 고쳤습니다. 측정 도구는 `tools/DeckSim`, 시뮬레이터는 `src/Sts2Overlay.Core/Simulation`입니다.

## 요약

|---|---|---|---|
| 빌드 완성 (주빌드 commit ≥ 0.7) | 96 % | 98 % | 99 % |
| 덱 일관성 (고른 카드 중 주빌드·테마 카드) | 35 % | 37 % | 40 % |
| 빌드 카드 중복 (같은 빌드 카드 추가 장수) | 0.80 | 1.65 | 1.68 |
| 덱 크기 | 30.1 | 31.8 | 34.2 (v2 통계 중앙값 31) |
| 빌드 이탈 (자리 잡은 빌드 카드가 나왔는데 다른 카드 추천) | 11.1 % | 7.6 % | – |
| 3막 카드 보상 스킵 (랭커 런 다시보기) | 77 % | 57 % | 44 % (v2 통계 52 %) |

- "고득점 카드를 빌드와 상관없이 추천한다"는 의심은 **지금 데이터로는 맞지 않습니다**. 빌드 밖 드로우 카드는 엔진 덱이 랭커 덱보다 오히려 적습니다(사일런트 3.6 vs 5.0장, 디펙트 1.9 vs 4.2장). 독 빌드의 드로우 문제는 PR #15 이후 해결된 상태입니다.
- 진짜 원인은 반대 방향이었습니다. 빌드를 **너무 얕게** 쌓았습니다. 코어 목록이 없는 빌드 11개는 보호 규칙을 하나도 받지 못했고(이탈 20~28 % vs 코어 있는 빌드 4~10 %), 빌드 카드 두 번째 장은 −15점을 그대로 받아 랭커처럼 겹쳐 쌓지 못했습니다.
- 랭커와의 1순위 일치율은 46 % 근처에서 거의 움직이지 않습니다. 그 이유와 "100 %가 목표가 아닌 이유"는 §6에 있습니다.

## 1. 무엇을 어떻게 쟀나

**시뮬레이터** (`RunSimulator`): 카드 쪽만 한 런 전체를 돌립니다.

- 맵 배치는 사용자 런에서 잰 막별 평균 방 구성(`RewardScheduler.TypicalActs`), 카드 보상은 게임 코드의 확률 그대로입니다: 일반 전투 희귀 3 %(A7+ 1.49 %), 엘리트 10 %(A7+ 5 %), 희귀 보정치 −5 %에서 시작해 희귀가 아닐 때마다 +1 %(A7+ +0.5 %), 막 × 25 %(A7+ 12.5 %) 확률로 강화된 카드. 1·2막 보스 보상은 희귀 3장.
- 상점: 공격 2 · 스킬 2 · 파워 1 + 무색 2, 한 장 세일(×0.5), 가격 흔들림 0.95~1.05, 카드 제거 75 + 25n(A6+ 100 + 50n). 골드는 경로 가중치의 방별 골드.
- 모델링하지 않은 것 [추정]: HP와 죽음, 시작 이후 유물, 포션, 휴식처 강화, 변환 이벤트, 고대의 선택지. 그래서 이 측정은 "덱을 어떻게 쌓나"만 보고 "이기나"는 보지 않습니다.

**정책 세 가지**를 캐릭터마다 400판(승천 10, 싱글 카드 풀, 시드 1000~1399)씩 돌렸습니다.

| 정책 | 카드 보상 | 상점 |
|---|---|---|
| engine | 오버레이 `RecommendationEngine`의 1위(스킵 포함) | 오버레이 상점 추천(구매 + 제거) |
| tier | 덱을 보지 않고 막별 티어 점수만, 스킵 점수보다 낮으면 스킵 | 티어가 가장 높은 카드 1장, 남는 돈으로 제거 |
| ranker | 시뮬레이션이 아니라 랭커의 실제 덱 | – |

**기준 데이터**: `docs/research/build-sources`가 인용한 OP.GG 상위 랭커 A10 솔로 승리 런 136개를 내려받아, 맵 지점이 60개를 넘는 비정상 기록 6개를 빼고 130개를 썼습니다. 런 원본(.run, Steam ID 포함)은 저장소에 넣지 않았습니다.

**랭커 런 다시보기**: 랭커가 실제로 본 카드 보상 화면 3,122개(상점 제외, 카드 2장 이상)를 그때의 덱 그대로 엔진에 넣어, 엔진의 1위와 랭커의 선택을 비교했습니다.

**덱 지표** (`DeckMetrics`): 카드 역할은 모두 팩 데이터(아키타입 목록, 티어 역할, 카탈로그 코스트)에서만 가져옵니다.

- 주빌드 = commit이 가장 높은 빌드. 빌드 완성 = 주빌드 commit ≥ 0.7. 코어 확보 = 주빌드의 core를 `coreTarget`장 보유(core 목록이 없는 빌드는 0으로 셈).
- 일관성 = 고른 카드(시작 덱·저주 제외) 중 주빌드 목록 + 주빌드 테마(`onTheme`, needs 축) 카드 비율.
- 에너지 곡선 = 고른 카드의 평균 코스트, 0/1/2/3+/X 비율, 장당 에너지(시작 덱 포함 전체 코스트 합 / 덱 크기).
- 드로우 카드 = 티어 `roles.draw` ≥ 0.4.

## 2. 수정 전에 본 것

### 2.1 빌드 완성 확률

엔진을 따르면 3막 끝 빌드 완성(commit ≥ 0.7)은 92~98 %로, 티어만 보는 정책(46~81 %)보다 확실히 높고 랭커(96~100 %)와 비슷합니다. **빌드를 고르고 끝까지 가는 것 자체는 잘 됩니다.** 다만 1막 끝 완성은 랭커보다 한참 낮습니다(엔진 20~47 %, 랭커 50~92 %). 1막은 "어떤 카드든 타격·수비보다 낫다" 규칙(`skip.basicPickBias`) 때문에 거의 스킵하지 않고(엔진 0~1 %, 랭커 10~19 %) 높은 티어 범용 카드를 먼저 받기 때문입니다.

### 2.2 덱 일관성과 빌드 이탈

자리 잡은 빌드의 카드가 보상에 나왔는데 엔진이 다른 카드를 추천한 비율(시뮬레이션, 3막 전체):

| 캐릭터 | 이탈 | core 있는 빌드 | core 없는 빌드 |
|---|---|---|---|
| 디펙트 | 17 % | 9 % | 27 % |
| 아이언클래드 | 18 % | 10 % | 21 % |
| 네크로바인더 | 9 % | 7 % | 28 % |
| 리젠트 | 4 % | 4 % | – |
| 사일런트 | 10 % | 5 % | 20 % |

core 목록이 없는 빌드(어둠 오브, 오브 다양성, 취약, 힘, 공격 반복, 타격 템포, 에테리얼, 교활·버리기 등 11개)에서 이탈이 두세 배였습니다. 코어를 잡은 뒤의 보호 규칙("빌드 필수 카드" 바닥 27점, 약점 상한 예외)이 **core 카드가 있는 빌드에만** 걸려 있었기 때문입니다.

### 2.3 빌드 카드 중복

3막 끝 같은 빌드 카드의 추가 장수: 엔진 0.4~1.0장, 랭커 1.3~2.2장. 랭커가 빌드 카드를 골랐는데 엔진은 다른 선택을 한 화면에서 엔진을 끌어낸 요소를 평균하면 `duplicate`(+15.5)가 기본 점수 다음으로 컸습니다. 랭커는 칼날 춤·망토와 단검 같은 빌드 카드를 두세 장씩 쌓는데, 중복 감점(장당 −15)은 빌드 카드와 범용 카드를 구분하지 않았습니다.

### 2.4 "과잉 생산" 감점이 빌드의 핵심 카드를 깎음

포화 규칙은 어떤 축(예: SHIV)을 만드는 카드가 쓰는 카드의 2배를 넘으면 그 카드의 시너지를 깎습니다(초과 1장당 15 %, 최대 70 %). 그런데 팩에서 "consumes" 태그를 단 카드는 드뭅니다(DISCARD 소비 1장, ORB_DARK 0장, ORB_FROST 1장). 그래서 빌드가 필요로 하는 축(`needs.tag`)에서 **랭커의 승리 덱도** 포화로 판정됐습니다.

| 빌드 | 축 | 랭커 덱 | 포화로 판정된 덱 | 남는 시너지 |
|---|---|---|---|---|
| 사일런트 시브 | SHIV | 36 | 39 % | 85 % |
| 사일런트 교활·버리기 | DISCARD | 10 | 100 % | 46 % |
| 아이언클래드 방어 | BLOCK | 5 | 80 % | 79 % |
| 네크로바인더 에테리얼 | ETHEREAL | 5 | 60 % | 82 % |

시브 덱에서 칼날 춤 −18.9점, 망토와 단검 −18.9점 같은 감점이 실제로 나왔습니다. 시브는 그 자체가 공격이라 "소비자"가 필요 없는데, 규칙은 그것을 과잉으로 봤습니다.

### 2.5 3막 스킵

| 막 | 랭커 스킵 | 엔진 스킵 (같은 화면) | v2 통계 (1,686판) |
|---|---|---|---|
| 1 | 15 % | 2 % | 14 % |
| 2 | 36 % | 33 % | 38 % |

## 3. 고친 것

### 3.1 core 없는 빌드도 "자리 잡으면" 보호 (`CardScorer.BuildSecured`)

core 목록이 없는 빌드는 서로 다른 필수 시너지(payoff + enabler)를 `essentialTarget`(기본 2)장 가지면 자리 잡은 것으로 봅니다. 이미 있던 "필수 시너지 → 서브 시너지" 단계와 같은 기준이라 새 숫자가 필요 없습니다.

```csharp
// 전: core 카드가 있는 빌드만 바닥값을 받음
var core = ArchetypeDetector.CoreProgress(s.Archetype, Pack, profile.Copies);
if (core.Target == 0 || core.Owned < core.Target) return default;   // core.Target == 0 → 항상 0

// 후: core가 있으면 core로, 없으면 필수 시너지로 판단
if (!BuildSecured(s.Archetype, Pack, profile.Copies)) return default;

public static bool BuildSecured(Archetype a, DataPack pack, IReadOnlyDictionary<string, int> copies)
{
    var core = ArchetypeDetector.CoreProgress(a, pack, copies);
    if (core.Target > 0) return core.Owned >= core.Target;
    var essential = ArchetypeDetector.EssentialProgress(a, pack, copies);
    return essential.Target > 0 && essential.Owned >= essential.Target;
}
```

같은 판단을 약점 상한 예외(약한 덱이어도 자리 잡은 빌드 카드는 상한 12 대신 25)와 "초반 방향 잡기" 보너스에도 씁니다. 세 곳이 서로 다른 기준을 쓰면 "바닥값은 받는데 상한에 막힌다" 같은 어긋남이 생기므로, 판단을 함수 하나로 모았습니다.

빌드와 상관없는 카드가 만드는 축(예: 독 덱에서 빌드 밖 드로우 카드의 DRAW)은 그대로 포화를 봅니다. 규칙을 처음 만든 이유였던 리젠트 별은 소비 카드가 많아서(별 덱 생산 5.5 / 소비 7.9) 원래도 포화가 걸리지 않았고, 이번 변경과 상관없습니다.

**2026-11 후속 수정 (보조 태그).** 처음 규칙은 축 하나하나를 빌드의 needs.tag와 비교했습니다. 그래서 빌드 카드가 needs.tag 말고 **보조 태그**를 함께 만들면 그 보조 태그로 포화 감점(시너지 점수의 최대 −70 %)을 받았습니다.
예: 냉기 빌드(needs `ORB_FROST`)의 냉정한 머리(`COOLHEADED`, provides `ORB`·`ORB_FROST`)는 `ORB` 소비 카드가 없어 냉기 덱이 완성될수록 깎였습니다.
번개(`BALL_LIGHTNING`)·어둠(`DARKNESS`, `SHADOW_SHIELD`)의 `ORB`, 사일런트 버리기 빌드(`PREPARED`, `ACROBATICS`)의 `DRAW`, 자해 빌드(`BLOOD_WALL`, `INFERNO`)의 `BLOCK`·`POWER`도 같았습니다.
이제는 기울어진 빌드가 그 카드를 역할 목록에 두었거나(`WeightOf(id) > 0`) 그 카드가 빌드의 needs.tag를 만들면, 그 카드의 다른 태그로도 포화를 매기지 않습니다.
회귀 테스트: `BuildStackingTests.A_build_producer_with_a_saturated_secondary_tag_is_not_saturated`(이전 코드에서는 실패).

### 3.3 빌드 카드 중복은 덜 깎음 (`buildDuplicateFactor` 0.4)

```csharp
// 전
var duplicate = -w.RhoDuplicate * copies * dupFactor;                       // 빌드 카드도 범용 카드도 −15/장

// 후: 그 카드를 목록에 둔 빌드의 (코어 반영) commit만큼 감점을 줄임
var buildRelief = memberships.Select(m => m.Commit * m.Gate).DefaultIfEmpty(0.0).Max();
var dupScale = 1 - (1 - w.BuildDuplicateFactor) * buildRelief;            // commit 1 → 0.4, commit 0 → 1
var duplicate = -w.RhoDuplicate * copies * dupFactor * dupScale;           // 확정 빌드 카드는 −6/장
```

`Gate`(코어 먼저)를 곱하기 때문에 core를 아직 못 잡은 빌드의 카드는 감점이 거의 그대로입니다. 0.4는 시뮬레이션 덱의 3막 끝 빌드 카드 중복이 랭커(1.68장)에 가장 가까운 값입니다(다른 수정은 그대로 두고 이 값만 바꿨을 때 1.0 → 1.07장, 0.6 → 1.41장, 0.4 → 1.65장, 0.25 → 1.82장).

**2026-11 후속: 0.4 → 0.3, 카드별 `dupFactor` 31장 보정.** 카드 점수 보정([`CARD_CALIBRATION.md`](CARD_CALIBRATION.md))으로 `baseAdjust`가 들어간 뒤 첫 장 카드끼리 점수 차가 커져서, 확정 빌드 카드의 두 장째(−6점)가 ±8~10점 보정 카드에 자주 밀렸습니다(중복 1.65 → 1.47장, 랭커 1.87장).
팩 값 `buildDuplicateFactor`를 0.3으로 내리고(확정 빌드 카드 −4.5점/장, 코드 기본값 0.4는 그대로), `pipeline.py fit`이 카드별 `dupFactor`도 맞추게 했습니다(CARD_CALIBRATION.md §9.1).
결과: 시뮬레이션 3막 끝 빌드 카드 중복 1.47 → **1.73장**(랭커 1.87장).

### 3.4 3막 스킵 기준 58 → 52 → 50 (`data/packs/v0.107.1/weights.json`)

2막과 같은 값입니다. 자리 잡은 덱의 스킵 점수가 57이 되어, **빌드 안 B 티어(64)는 통과하고 빌드 밖 B 티어(50 − 빌드 밖 10 = 40)는 여전히 스킵**합니다. 덱이 커지는 것은 기존 `skip.lambdaSize`(이상 크기 31장 초과 1장당 +1.5)가 계속 막습니다. 코드 기본값(58)이 아니라 팩 값만 바꿨습니다.

**2026-11 후속: 52 → 50.** 카드 점수 보정에서 2·3막 즉시 피해·광역 긴급도를 낮춘 뒤 3막 카드의 need 점수가 평균 2점쯤 줄어, 엔진의 3막 스킵이 랭커보다 많아졌습니다(58 % vs 48 %, 승리 런 리플레이). 50으로 내린 뒤 리플레이 3막 스킵 **50 %**, 3막 끝 덱 크기 31.81 → 32.47장(랭커 32.56장)입니다.

### 바꾸지 않은 것

- **1막 스킵**(엔진 0~1 % vs 랭커 15 %): `skip.basicPickBias`는 "시작 덱에서는 어떤 카드든 타격·수비보다 낫다"는 의도된 규칙이고 테스트로 고정돼 있습니다. 승천이 낮은 2인 협동에서는 이 편이 맞을 수 있어 그대로 둡니다.
- **코어 먼저**: core를 아직 못 잡았는데 그 빌드에 기울어 있을 때, 랭커는 그 빌드의 core 아닌 카드를 57 % 집었고 엔진은 40 % 집었습니다. "core 전에는 시너지를 거의 반영하지 않는다"(`noCoreFactor` 0)는 규칙의 결과입니다. 사용자가 고른 설계라 바꾸지 않았고, 완화하려면 `corePriority.noCoreFactor`를 0.3쯤으로 올리면 됩니다(시뮬레이션에서 일치율 45.9 → 46.1 %, 덱 지표는 거의 같음).
- **2막 스킵 기준**: 52 → 55로 올리면 랭커 스킵률(36 %)과 같아지지만(엔진 28 → 37 %) 일치율·덱 지표가 거의 변하지 않아 근거가 약했습니다.

## 6. 일치율이 100 %가 목표가 아닌 이유

1. **같은 화면에서도 정답이 하나가 아닙니다.** 랭커가 고른 카드는 엔진 순위 1위가 53~58 %, 2위까지 82~84 %입니다. 남는 차이의 상당수는 "B 티어 두 장 중 무엇" 같은 1~3점 차이라, 사람마다·런마다 다르게 고르는 영역입니다. 랭커 130판 안에서도 같은 빌드끼리 고르는 카드가 다릅니다.
2. **스킵은 화면만 봐서는 잘 갈리지 않습니다.** 3막에서 엔진의 스킵 권유는 랭커가 스킵한 화면(65 %)과 카드를 고른 화면(51 %)에서 크게 다르지 않습니다. 랭커의 스킵은 다음 엘리트, 남은 HP, 유물, 포션처럼 이 측정이 보지 않는 정보에 달려 있습니다. 그래서 스킵을 줄이면 랭커와 같은 비율에 가까워져도 1순위 일치는 조금 떨어집니다(3막 기준 58 → 52에서 46.6 → 45.9 %). 같은 이유로 "빌드 이탈"도 6.9 → 7.6 %로 조금 늘었습니다. 전에는 스킵하던 화면 일부에서 빌드 밖 카드를 고르기 때문입니다. 엔진이 카드를 고르면 랭커의 카드와 같을 확률이 58 %뿐이라, 랭커가 스킵한 화면 하나를 잃는 손해가 더 크기 때문입니다. 이번에는 일치율 대신 **스킵 비율과 덱 모양**을 랭커에 맞췄습니다.
3. **표본이 사용자 게임과 다릅니다.**
   - 랭커 런은 빌드 근거 문서에 "모범 사례"로 인용된 130판입니다. 덱이 큰 런 쪽으로 치우쳐 있습니다(3막 끝 34.2장, 랭커 1,686판 전체 중앙값 31장). 캐릭터별 n은 12~50이라 빌드별 비교(n = 5~36)는 방향만 봅니다.
   - 모두 A10 솔로입니다. 사용자는 주로 낮은 승천의 2인 협동이라, 위험을 덜 지고 카드를 더 받는 편이 맞을 수 있습니다(1막 스킵을 바꾸지 않은 이유).
   - 시뮬레이션은 HP·유물·포션·변환을 모델링하지 않고, 시작 덱·유물은 캐릭터별 첫 랭커 런의 것입니다.

그래서 이 측정은 "추천이 랭커와 똑같나"가 아니라 **"추천을 따르면 랭커 같은 덱이 나오나"**(빌드 완성, 일관성, 겹쳐 쌓기, 크기, 곡선)로 봐야 합니다. 그 기준에서는 수정 후 덱이 랭커 쪽으로 움직였습니다.

## 8. 다시 재기

```bash
dotnet run --project tools/DeckSim -c Release -- --pack data/packs/v0.107.1 --rankers <랭커 .run 폴더> --n 400 --out report.md --json summary.json
```

- `--policies engine,tier`, `--asc 10`, `--mp`(협동 카드 풀), `--diag 12`(예시 수).
- `--set skip.t0.3=52 --set buildDuplicateFactor=0.6 ...`로 가중치를 바꿔 보고, `--line`은 한 줄 요약(일치율, 막별 스킵, 혼합 화면, 이탈, 중복, 크기, 일관성, 코어 확보)을 출력합니다. 가중치를 바꿀 때 이 한 줄을 전후로 비교하면 됩니다.
- 랭커 런은 OP.GG 런 페이지에 들어 있는 .run JSON을 저장한 파일입니다. Steam ID가 들어 있으니 저장소에 넣지 마세요. 보고서에는 집계와 OP.GG 런 번호만 나옵니다.
